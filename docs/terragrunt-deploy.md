# Deploying the rustkube masters with Terragrunt

How to bring up (and safely operate) a 3-master cluster on Proxmox VMs (Fedora)
with Terragrunt. **This is not how stormcos runs rustkube** — stormcos ships
each component as a stormd golden (see the README's *How it ships*). This path
predates it.

> **It cannot install a current rustkube as written.** cloud-init installs the
> newest `x86_64` RPM from the **latest** GitHub release
> (`install-latest-rpm glennswest/rustkube`), and no release since **v0.7.30**
> carries an RPM: CI attaches musl tarballs and scratch images only
> ([releasing.md](releasing.md)). A fresh provision fails at that step until
> CI publishes the `kubernetes-rs` RPM again (`deploy/packaging/nfpm.yaml`) or
> the template installs the tarballs. Checked 2026-09-24 (#80).

Unit: `deploy/terragrunt/masters/` → `master1/2/3.g8.lo` (192.168.8.51/.52/.53,
VMIDs 2000–2002). Each master runs a fastetcd raft member, kube-apiserver,
kube-controller-manager, kube-scheduler, and — from the rustkube-node RPM —
CRI-O, the kubelet and kube-proxy; master1 also runs `bootstrap-cilium`. The
`workers` map in `terragrunt.hcl` exists and is empty.

## Project structure

```
deploy/terragrunt/
  root.hcl                 # provider + token wiring (generated into every unit), once
  free-vmid.sh             # VMID allocator shim (default range 2000-2100)
  masters/                 # THE control-plane unit (3 masters)
    terragrunt.hcl         # nodes (no version pins), PKI wiring, module source
    templates/master-user-data.yaml.tftpl   # cloud-init for a master
    templates/worker-user-data.yaml.tftpl   # cloud-init for a worker
    pki/                   # generated by gen-pki.sh (gitignored), incl. tokens/<node>
    .terraform.lock.hcl
  tclusters/               # tcluster1-4, tnode1: test clusters (deploy/new-tcluster.sh)
```

- `root.hcl` only generates the provider. Each unit's `terragrunt.hcl` names
  the shared, versioned module
  (`git::ssh://git@github.com/glennswest/terraform-modules.git//modules/proxmox-fedora-vm?ref=v0.3.0`)
  — units never copy `.tf`; they reference the module by tag.
- The `masters/` unit supersedes the older single-node `fastetcd/` + `rustkube/`
  units still mentioned in `deploy/terragrunt/README.md` (that README is stale;
  use this doc).

## Prerequisites

- `terragrunt` + `terraform` (or `tofu`), `jq`, `openssl`, `curl`, `python3`.
- **Proxmox API token** for the `terraform-svc@pve` service account, in the
  environment (never in code/state) — it must have ACL scope over this project's
  pool/storage (`test-lvm-thin` for disks, `terraform-snippets` for cloud-init):
  ```bash
  export PROXMOX_API_TOKEN='terraform-svc@pve!<tokenid>=<uuid>'
  ```
  The token is set once per shell; every `terragrunt`/`gh`/`curl-to-pve` command
  in that shell inherits it. Proxmox never re-displays a token secret, so store
  it safely.
- SSH public key at `~/.ssh/id_rsa.pub` (injected for the `fedora` user).
- A GitHub release of rustkube (and of fastetcd and rustkube-node) whose
  assets include an `x86_64` RPM — see the warning at the top. There are no
  version pins: whatever is latest is installed.

## 1. Generate the PKI (once)

```bash
./deploy/gen-pki.sh          # → deploy/terragrunt/masters/pki/ (gitignored)
```

Creates the cluster CA, the SA keypair (`sa.key`, `sa.pub`), per-master
serving certs (with SANs), component/admin client certs, the node bootstrap
cert, and a kubelet token per node under `pki/tokens/<node>`. Idempotent — reruns
keep the existing CA. Terragrunt injects these via cloud-init.

## 2. Deploy

```bash
cd deploy/terragrunt/masters
terragrunt init
terragrunt plan       # review: expect 9 to add on a clean cluster
terragrunt apply
```

All 3 masters boot together, install the fastetcd, kubernetes-rs and
rustkube-node RPMs, form the raft cluster, and start the TLS control plane and
the node components.

### How the cloud-init works

Terragrunt renders `templates/master-user-data.yaml.tftpl` per master and uploads
it to the Proxmox `terraform-snippets` datastore as
`<master>-user-data.yaml`; the VM's `user_data` points at that snippet, so
cloud-init runs it on first boot. Flow:

- **Terragrunt → template variables** (`terragrunt.hcl`, `inputs.vms[*].user_data`):
  hostname/IP, the fastetcd `initial_cluster` + `etcd_servers` lists, the
  node's pod CIDR, and every PKI file read via `file("${local.pki}/…")` (CA, SA
  keypair, per-master serving cert/key, component + admin client certs, the
  node's kubelet token). PEM blobs are indented into the YAML with `indent(6, …)`.

- **`write_files`** lays down:
  - `/etc/fastetcd/fastetcd.conf` — `ETCD_*` env (name, data dir, listen/advertise
    URLs, `ETCD_INITIAL_CLUSTER`, token, `ETCD_INITIAL_CLUSTER_STATE=new`).
  - `/usr/local/bin/install-latest-rpm` — resolves and `dnf install`s the
    newest x86_64 RPM of a repo's latest release.
  - `/etc/kubernetes/pki/*` — ca.crt, ca.key, sa.key, sa.pub, apiserver.crt/key,
    controller-manager.crt/key, scheduler.crt/key, admin.crt/key (keys `0600`).
  - `/etc/kubernetes/kube-apiserver` — `ETCD_SERVERS` + `KUBE_APISERVER_ARGS`
    (`--tls-cert-file … --tls-private-key-file … --client-ca-file …
    --service-account-signing-key-file …/sa.key --service-account-key-file
    …/sa.pub --advertise-address <ip> --anonymous-auth=false`).
  - `/etc/kubernetes/kube-controller-manager` and `…/kube-scheduler` —
    `APISERVER_URL=https://127.0.0.1:6443` + client-cert args (and, for the CM,
    `--cluster-signing-cert-file`/`--cluster-signing-key-file` for CSR signing).
  - `/etc/kubernetes/kubelet-token`, `/etc/kubernetes/kubelet`,
    `/etc/kubernetes/kube-proxy`, `/etc/kubernetes/admin.kubeconfig`, and
    `/usr/local/bin/bootstrap-cilium`.
  These paths match the systemd units' `EnvironmentFile=` and `$KUBE_*_ARGS`.

- **`runcmd`** (order matters):
  1. `install-latest-rpm glennswest/fastetcd` — all 3 install together and
     form the raft cluster (the RPM's postinstall does `enable --now fastetcd`).
  2. `install-latest-rpm glennswest/rustkube` — lays down the upstream-named
     binaries + units (postinstall does daemon-reload, not enable). **Fails
     today** — see the top.
  3. `systemctl enable --now kube-apiserver kube-controller-manager kube-scheduler`
     — started after fastetcd so `--etcd-servers` is reachable (units retry until
     quorum forms).
  4. CRI-O, then the rustkube-node RPM's kubelet and kube-proxy; master1 runs
     `bootstrap-cilium`.

To see it on a node: `sudo cat /var/log/cloud-init-output.log`, and
`cloud-init status` (`done` when finished).

## 3. Verify

`deploy/verify-cluster.sh` predates TLS here: its `plaintext` mode curls
`http://…:6443`, which these apiservers refuse, and its `tls` mode overwrites
`KUBE_APISERVER_ARGS` with `--tls`. Check directly, with the admin cert:

```bash
cd deploy/terragrunt/masters/pki
for ip in 192.168.8.51 192.168.8.52 192.168.8.53; do
  curl -s --cacert ca.crt --cert admin.crt --key admin.key https://$ip:6443/healthz
done
```

Expect `ok` on all three, `anonymous → 401`, and namespace writes replicated
across masters.

## Operating: upgrades and replacement

### Version upgrade (preferred) — in-place, no data loss

For a new rustkube version, **upgrade in place** — do NOT recreate VMs:

```bash
RPM="https://github.com/glennswest/rustkube/releases/download/vX.Y.Z/kubernetes-rs-X.Y.Z-1.x86_64.rpm"
for ip in 192.168.8.51 192.168.8.52 192.168.8.53; do
  ssh fedora@$ip "sudo dnf install -y $RPM && \
    sudo systemctl restart kube-apiserver kube-controller-manager kube-scheduler"
done
```

This needs a release that carries an RPM (v0.7.30 was the last). There is no
pin to bump: new provisions take the latest release. This keeps fastetcd (and
all cluster data) untouched.

### Replace ONE master (safe — keeps the cluster + data)

**Never** `-target destroy` one VM then a full `apply` — that cascades into
recreating all three and wipes fastetcd (see gotcha #2). Use the runbook, which
does the etcd member dance (the manual equivalent of OpenShift's
cluster-etcd-operator) + a scoped `-replace`:

```bash
cd deploy/terragrunt/masters
../../replace-master.sh master1     # remove old member → add new member →
                                    # -replace only that VM (state=existing) → rejoin
```

It targets the raft **leader** for member ops (fastetcd doesn't forward them —
fastetcd#7), recreates only the one VM, and the node boots
`ETCD_INITIAL_CLUSTER_STATE=existing` (via the `RK_REPLACE_MASTER` env → the
template's `cluster_state`) so it rejoins instead of bootstrapping anew.
Requires `etcdctl` + `jq` on PATH and `PROXMOX_API_TOKEN` set.

### Full redeploy (destroys all data)

```bash
terragrunt destroy -auto-approve
terragrunt apply   -auto-approve
```

Recreates all 3 masters from scratch — **fastetcd starts empty**. Only for a
clean rebuild.

## ⚠️ Gotchas (hard-won)

1. **Never `rm -rf .terragrunt-cache`.** The local tfstate lives under it. Delete
   it and Terragrunt loses track of the running VMs; the next `destroy` finds
   nothing and the next `apply` re-adopts or duplicates. To pick up edited
   templates, just re-run `terragrunt init` (it re-copies the unit).

2. **Do NOT replace a single master with `-target destroy` + full `apply`.**
   A partial `-target destroy` of one VM followed by a non-targeted `apply`
   **cascades into replacing all three masters** (observed: `6 added, 5 destroyed`),
   which wipes fastetcd and loses all cluster data. Verified via the HA soak test.
   - For a version change → use the **in-place upgrade** above.
   - To replace one member → `replace-master.sh`, above, which does the member
     remove/add and boots the new VM with `ETCD_INITIAL_CLUSTER_STATE=existing`.

3. **Master *loss* is safe; master *recreate* is not (yet).** Losing one master
   (VM stop/destroy) leaves the cluster fully serving on the other two (raft
   quorum 2/3, data intact). It's the *recreate* path that currently risks the
   cascade above.

4. **Host keys change on every recreate.** Use
   `-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null` for SSH to
   freshly-provisioned masters, or clear stale keys with `ssh-keygen -R <ip>`.

5. **`gen-pki.sh` must run before apply** — the template reads the PKI files via
   `file()`. Missing files → a plan/apply error. Regenerate is idempotent (keeps
   the CA); add new cert types and re-run.

6. **After editing `terragrunt.hcl` or a template, re-run `terragrunt init`.**
   Otherwise `plan` can report **"No changes"** against a stale cached copy of
   the unit and you'll deploy the old template. Symptom: you changed the
   cloud-init but the booted node still runs the old config. (Re-init re-copies
   the unit into `.terragrunt-cache`; do **not** `rm -rf` the cache — see #1.)

7. **`fastetcd-ctl` is a minimal etcd client.** It uses `--endpoint` (singular),
   and only has `put/get/del/snapshot-save` — there is no `endpoint health` /
   `member list`. Check liveness with `systemctl is-active fastetcd` + a
   `fastetcd-ctl --endpoint http://127.0.0.1:2379 get --prefix /registry/…`
   (per-node key count proves raft replication).

8. **SSH as `fedora@<ip>`** with the key injected at provision (`~/.ssh/id_rsa`).
   Combine with gotcha #4's options on freshly-recreated hosts.

## Scale + HA soak test

```bash
./deploy/ha-soak-test.sh scale-only   # 1000 namespaces: create/delete/recreate, verify replication
./deploy/ha-soak-test.sh              # + kill a master, verify survival, recreate, verify
```

Phases: **1 (scale)** and **2a (master loss → cluster survives, data intact)**
pass. **2b (safe replace via `replace-master.sh`)** recreates only the one VM
(no cascade) and the node rejoins. It found two bugs, both since fixed:
**fastetcd#8** (a rejoined member did not resync its MVCC store; closed) and
**rustkube#18** (the watch cache could serve a stale LIST when its upstream
watch stalled; fixed in v0.7.3).
